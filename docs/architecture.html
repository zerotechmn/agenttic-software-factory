FORGE: how the factory works

FORGE is an autonomous software factory. One command takes a written brief and runs a team of AI agents: product, research, architecture, design, parallel developers, review, QA, release review and deploy. It ends with a tested, running app and a report. This page explains the architecture, the order things happen in, why each guardrail exists, and how to operate it.

1Overview

FORGE has a deterministic orchestrator and intelligent workers.

The orchestrator is ordinary TypeScript
It decides who works next, gives each worker its files, runs the checks, merges, retries and tracks spend. It makes no model calls itself, so the order of work and the rules are the same on every run.
The workers are Claude agents
Each role (Product, Architect, Developer…) is a Claude Agent SDK session. It gets its own system prompt (roles/*.md), tools, skills, model and budget. Workers communicate only through files in the repo, never in a shared chat.
Every decision is visible
Every action is appended to .forge/events.jsonl. Every judgement call (a ruling) goes into .forge/ledger.md. The Office UI animates the events live, and you can replay them later.
./forge run samples/briefs/wheels2go.md --budget 20   # brief in, deployed app out
./forge console                                  # Office UI at http://localhost:4300/office/

Why the orchestrator is not an LLM: a model deciding "who works next" can drift, loop or forget a step. FORGE keeps the control flow in code: phases, gates, retry limits, budgets and merges. Models are used only for the creative work in each step. That keeps runs reproducible and keeps cost bounded.

6Worktrees, explained

This is how three developers can write code at the same time without overwriting each other.

The problem. If three agents edited the same folder at once, one would save App.tsx while another was halfway through editing it. Tests would run against half-written code from someone else, and nobody could tell whose change broke what.

The fix: a git worktree. A worktree is a second (third, fourth…) checkout of the same git repository in a different folder, each on its own branch. There's one repository and one history, but several working copies. When developer A starts task T-3, the orchestrator runs:

git worktree add .forge/wt/T-3 -b t/T-3     # a private copy of main, on branch t/T-3

Developer A only works in .forge/wt/T-3. Developer B is in .forge/wt/T-4. Neither can see the other's half-finished work. That's intentional, because each task is built and tested against a clean, known-good main.

Passing work between agents. Agents never hand code to each other directly. The handoff always goes through main:

  1. A finishes, and the orchestrator runs the gate (typecheck, lint, unit tests) inside A's worktree.
  2. The Reviewer checks A's diff.
  3. The orchestrator merges t/T-3 into main. Merges happen one at a time behind a lock.
  4. It runs the gate again on main. If main is now broken, that one merge is reverted and A gets the error as feedback.
  5. The next task that starts (or a task that has to re-merge) begins from the new main, so it gets A's work.

When two tasks touch the same lines, the merge conflicts. The Integrator merges main into the task's worktree, resolves the conflict keeping both intents, re-runs the gate, and then the merge is retried.

Why it works without agents talking to each other: before any developer starts, the Architect freezes the contracts (src/shared/contracts.ts: the API types, the DB schema, the routes). Each developer codes against those agreed types. Two developers who never met still produce pieces that fit, the same way two companies can build to one published API.

7Guards: why a developer can't touch e2e tests (and other files)

Every file write and shell command an agent attempts first goes through guard.ts, a PreToolUse hook. If it isn't allowed, the tool call is denied with a reason before anything happens on disk.

1. Stay in your own folder
A developer may only write inside its own worktree. Paths with ../, absolute paths elsewhere, or a cd out are denied. Otherwise one agent could edit another agent's worktree, or your machine.
2. Stay in your lanes
Each task has lanes: the globs it owns, for example src/web/catalog/**. The architect assigns lanes that don't overlap, so parallel tasks rarely conflict. Touched read-only files are also restored before the merge.
3. Never edit the referee
These are core-protected for every developer, always: tests/e2e/**, tests/acceptance/**, docs/**, .forge/**, src/shared/contracts.ts, CLAUDE.md.

Why e2e tests in particular

The e2e and acceptance tests are QA's proof that the product does what the PRD promised. If the developer whose code is being tested could also edit those tests, the easy way out of a failing test would be to weaken or delete it. The test would pass and the feature would still be broken. (Models really do this under pressure: "fix the test" is easier than "fix the bug".)

So the people who write the code never write its exam. QA owns e2e, the Architect owns contracts, and Product owns the PRD. A developer who thinks a test or contract is wrong reports BLOCKED with the reason. The orchestrator then decides; it might widen a fix task's lanes once or send the note back. A developer never quietly changes the rules.

The other protected files

FileWhy a developer can't change it
src/shared/contracts.tsThe agreement every parallel developer codes against. Changing it in one worktree breaks the others when they merge.
docs/** (PRD, design, tasks)These are the spec. Changes come from the operator (forge iterate change requests), not from the builder.
.forge/**The orchestrator's own state, ledger and budget. An agent must not be able to edit its own score.
package.json, configs, schema.tsRead-only unless the task's lanes explicitly include them. That stops dependency drift from three developers adding packages at once.
What the guard is not: it isn't a security sandbox against a malicious model. It keeps well-meaning agents in their own work, so mistakes stay small and can be traced. Docker and the deterministic gates are the second line.

10Lessons: learning across runs

After every run the Learner reads what failed (gate failures, guard denials, QA findings, rulings) and adds or reinforces short lessons in lessons/lessons.json, for example "Never put tests/e2e/** in a dev task's lanes." Each lesson has a role, a trigger, a confidence score and the runs it came from.

flowchart LR
  E[run events
failures · denials · QA] --> L[Learner · haiku]
  L -->|new or reinforce| J[(lessons.json)]
  J -->|confidence ≥ 0.5| P[injected into that role's
system prompt next run]
  J -->|≥ 0.85 and seen in 3+ runs| PR[forge lessons promote
→ written into roles/*.md]
  J -->|proven wrong| RT[retired · confidence lowered]

Lessons ship with the repo: it's the factory's memory, and each entry shows which run it was learned from.

11Console and Office

forge console starts a localhost server. It lists runs, streams each run's events.jsonl over Server-Sent Events, and serves the Office, a PixiJS pixel office where every role is a character at a desk.

  • Live or replay: any finished run replays from its event log at 1×, 4× or 10×. With no console, the Office replays a bundled sample run.
  • Operator input goes in through files (an inbox) that the orchestrator reads between steps. The UI never touches the run directly.
  • Cost separation: handoff dialogue is billed to .forge/dialogue-usage.json, outside the build budget.

13Operator guide

CommandUse
forge run <brief.md> [--budget USD] [--concurrency N]Start a run. Prints the run folder.
forge console [--port 4300]Office UI for all runs. Answer PRD questions and send notes from here.
forge status <dir> / forge stop <dir>Check progress / stop cleanly at the next checkpoint.
forge resume <dir> [--budget USD] [--retry-parked]Continue a stopped or finished run.
forge iterate <dir> "change 1" "change 2" [--lanes "src/**"]Operator change requests: they become fix tasks and override the PRD for QA and review. Then resume.
forge report <dir>Regenerate RUN_REPORT.md.
forge lessons [promote <id>]Inspect lessons; promote a proven one into its role file.

On the day

  1. Start forge console first and open the Office. Click once anywhere so the browser allows sound.
  2. forge run brief.md --budget 20.
  3. When Product's questions appear in the PRD panel, answer them all in one message (for example, rental days count nights).
  4. Leave it alone. Every manual intervention counts against autonomy.
  5. When it finishes, the app is on the brief's port (default 8800) and the report is in docs/RUN_REPORT.md.
